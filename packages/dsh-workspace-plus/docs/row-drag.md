# 行拖拽

dsh-workspace-plus 侧边栏里的五类行——置顶会话、会话、会话分组、工作区、虚拟工作区——都可以被拖动，完成归组与排序两类操作。会话行只做归组与移出（不做段内排序，见「会话段没有顺序位」），置顶行与另外三类行做排序。本文记录这套拖拽基础设施的架构与顺序存储：手势怎么收、落点怎么算、顺序存哪里、多个拖拽环境怎么共存。

实现分布在 `src/client/hooks/useDnd.ts`（机制层）、`src/client/data/dnd.ts`（计划构造）、`src/client/data/tree.ts`（工作区与虚拟分组的统一节点树）、`src/client/data/dropSearcher.ts`（唯一的落点检测入口）、`src/client/data/move.ts`（一次移动要写哪几笔）、`src/client/data/pinned.ts`（置顶顺序合成与段键）。本文是它们的架构说明，不逐文件复述。

## 总体架构：计划驱动

### 四层分离

| 层 | 职责 | 认识业务吗 |
| --- | --- | --- |
| 手势层 | 收原生拖放事件，维护「当前有一场拖拽」 | 不认识 |
| 命中层 | 指针 → DOM 标记 → 区域键与参照行 | 不认识 |
| 计划层 | 这次拖拽能落到哪、落到之后写什么 | 全部业务知识在这里 |
| 持久层 | 顺序与归属的读写 | 宿主方法与存储域 |

核心概念是**拖拽计划**：`dragstart` 那一刻，由发起拖拽的业务侧（行所在的容器组件）构造一份计划，声明「我是谁、我能落到哪些区域、落到每个区域之后执行什么」。计划是整个架构里唯一含业务知识的东西，手势层与命中层只认计划里的键。

```ts
/** 被拖对象，类别由类型表达 */
export type DragSource =
  | { kind: 'session'; id: string }
  | { kind: 'sessionGroup'; workspaceId: string; groupId: string }
  | { kind: 'workspace'; id: string }
  | { kind: 'virtualWorkspace'; groupId: string }

/** 落点：整块落进容器，或插到某行之前 / 之后 */
export type DropAnchor =
  | { kind: 'inside' }
  | { kind: 'before'; rowId: string }
  | { kind: 'after'; rowId: string }

/** 计划里的一个目标区域 */
export interface DragPlanTarget {
  /**
   * 落点给什么档
   *
   * `container`：整块只接 inside
   * `rows`：按区域内的行算 before / after，指针落在段内空白（行与行之间的缝隙、段尾）时读作追加到段尾
   *
   * 第三种读法「同一格上两种都成立、按指针在带里的位置分流」服务分组嵌套，
   * 那一能力尚未实现，因此**不在这个联合里**：类型上不出现，外部就不会以为它现在能用。
   * 判定点留在检测层，见「纵向三分带留给分组嵌套」
   */
  mode: 'container' | 'rows'
  /**
   * 这一片的落点单位由哪一格代言
   *
   * 一片可以占好几格（工作区的标题行与体内那一格、虚拟分组的组头与组体），
   * 而框与线只画在一个元素上。缺省表示这一格自己就是单位（「只有一行的块」）
   */
  regionOf?: string
  /** 放开时执行。闭包在计划构造时绑定全量顺序等数据，执行前自行复核 */
  commit: (anchor: DropAnchor) => void
}

/** 一次拖拽的完整计划，dragstart 时构造，dragend 时销毁 */
export interface DragPlan {
  source: DragSource
  /** 键与 DOM 标记上的区域键一一对应；不在表里的区域这次拖拽就不接 */
  targets: ReadonlyMap<string, DragPlanTarget>
}
```

### DOM 上的静态与拖拽期标记

```ts
'data-wg-dnd': string          // 区域键，如 'sessionGroup/ws-1/g-2'、'loose/ws-1'、'pinned'、'root'
'data-wg-dnd-row': string      // 可作 before/after 参照物的行 id
'data-wg-dnd-scope': string    // 一个可整块压淡的区块（今天挂在工作区块上）
'data-wg-dnd-scroll': string   // 拖拽期间可以跟着指针自动滚动的容器
'data-wg-dnd-dim': string      // 本次拖拽够不着，由命中层在拖拽期间写上
'data-wg-drop': string         // 当前落点，取值是落点形状（before / after / inside）
```

前四个由业务渲染期写好、**拖拽期间不变**；后两个由机制层在拖拽期间写、结束时清掉，React 从不渲染它们。与「区域在拖拽期间按来源类别换属性」的做法相比，DOM 完全被动：同一个分组头，在「会话计划」里它的键配 `container` 档（读作归组），在「分组计划」里同一个键配 `rows` 档（读作插到它前后）——含义由计划决定，不由元素决定，元素不需要知道自己正被哪种拖拽划过。

### 一次拖拽的生命周期

1. 行上的 `dragstart`：行业务侧构造计划，调 `beginDrag(plan)`。计划被写入模块级单例 `currentPlan`，手势层往 `document` 挂 `dragover` / `drop` 接管，同时按计划给够不着的那几片写上 `data-wg-dnd-dim`，并起一轮边缘自动滚动。
2. `dragover`：适配层把事件目标换成**节点身份**（`nodeAt`），检测器沿树往上走出那条链，取链上第一个在名单里的节点。区域目标是 `rows` 档时按指针正落着的那条带算前后半（量不出高度时读 `before`）。检测结果交回的是两个节点，再由绘制表映射回元素、写落点标记（`data-wg-drop="before|after|inside"`，移走时删掉）。指针位置同时被记下，供自动滚动那一帧使用。
3. `drop`：取当前命中，查计划拿到 `commit`，执行。提交只发生一次。
4. `dragend`：清标记与压淡、停自动滚动、摘监听、清单例。

### 落点关系由树一次给全

**计划层不认识节点身份。** `workspaceTreeDragPlan` 的整个函数体只有一句实质内容：向树要一份关系表，然后按关系接线。它不再判「是不是祖先」「是不是同层」「在不在根节点那层」——那些都是树的内部事实。

树交出的每一条关系自带两样东西：

```ts
{ kind: 'inside', zones: string[], commit: () => void }
{ kind: 'order',  zones: string[], place: (side) => void }
```

`zones` 是这条关系在界面上占的那几格。计划层只做「把这几个区域键指向这条关系」，因此三条来源（cwd 祖先、虚拟分组归属、会话分组归属）的差别在树里面就消掉了，外面只看到「存在哪些关系」。

**一条行只有一种身份**仍然成立，但它现在是树的内部判据，不再泄漏到调用方：能给框的行（祖先工作区）放进 `inside`，能给线的行（同层兄弟、根节点平铺行）放进 `order`。一条行不会同时出现在两边。

### 一条行只有一种身份：要么是容器，要么是参照行

一条工作区行能不能承接放入，只看它是不是**容器**。对用户来说，虚拟工作区分组与按 cwd 推导出来的父工作区是同一类东西：都是能把工作区收进去的容器。因此落回祖先工作区那一行，读作「成为它的子工作区」，写 `moveWorkspace` 或 `nestWorkspaces`。

容器身份与参照身份**互斥**。一个工作区不会既被放进某个容器、又与那个容器的行谈先后——它已经确认自己要作为子工作区出现在那个容器里，再与容器的行排序没有意义。因此祖先工作区那一行先按容器判，只有剩下的行才轮到同层换位。

反过来说，一条既不是自己的祖先、又不是自己的同层兄弟的行，**不是容器**，落到上面不接：既不画框也不画线。

**根节点那一层的平铺行是例外**：它代表「不在任何虚拟分组里」这一片本身。来源在某个分组里时，落到这些行上读作「移出分组、回到与它们同级的位置」，写 `moveWorkspace('')`——用户要把工作区放到与根节点那几条同级的位置时，正是这一手，因此必须给框。已经在根节点那一层时落上去仍是原地投放，不接。

别的虚拟分组里的行不在此列：那一片由分组自己承接落点，落到其中某一行上若也读成「移进那个分组」，指针下的那一行与真正要去的容器就不是同一个东西了。少了这一条，任何一行都会顺着「它所在的容器」被读成「移进那个容器」，拖到一条毫无归属关系的行上也会亮起放入框。

### 纵向三分带：留给分组之间的嵌套

**这一档今天不存在，名字先记在这里。** 它的读法是「同一格上两种都成立，按指针落在这条带的哪一段分流」：上四分之一读 `before`、下四分之一读 `after`、中二分之一读 `inside`。

它给的是**容器对容器**的情形：一个分组既能承接放入（成为它的下级），也能与另一个分组谈先后。拖拽的对象本身就是容器时两种读法才并存。

### 为什么它不在类型里

`DragPlanTarget.mode` 只有 `container` 与 `rows` 两档。第三种读法**服务分组嵌套，而分组嵌套尚未实现**，没有任何用例能证明它是对的。把它留在公开类型里，读代码的人会以为它已经能用——这比缺一个功能更糟，因为它不会报错，只会在真被使用时给出错误的行为。

因此取舍是：**入口留一条，对外接口不留。** 判定点放在检测层（`dropSearcher.ts` 的 `checkDrop`），那一处同时握着框与线的答案，是两个答案唯一能互相比较的地方。今天走到那里会报错，报错信息说明分组嵌套尚未实现。

### 将来接回来要改哪几处

**改动集中在中间层，渲染与手势一行不用动**——这条边界是这个模块能被安全迭代的前提，下面三处都落在它里面：

1. `tree.ts` 的位次关系只给 workspace 节点算（`if (other.kind === 'workspace')`），虚拟分组因此没有位次关系。做分组嵌套时要让它也参与。
2. `tree.ts` 的 `isAncestorRow` 保证祖先工作区只承接放入、不当位次参照。分组嵌套要允许「既是容器、又是参照」并存，这一条要放宽。
3. `dropSearcher.ts` 的 `checkDrop` 把那条报错换成真实分流，并按需引入带高比例（今天没有这个常量，别处也没有引用它）。

**这条路径之所以还算便宜，靠的是中间层的边界本身**：判定在 `tree.ts` 与 `dropSearcher.ts`，渲染只负责把结果画出来。一旦某次重构把判定散回渲染层，上面三处的改动面就会扩大。守住这条边界比守住这段文字重要。

### 一次投放两笔写入：也还没有合成

拖一条工作区进分组时，框说「放进这一组」、线说「排在组内某一行之前」。这两件事**本来就是同一件事的两半**：只做其中一半，界面上就会出现「进去了但位置不对」或「位置对了但没进去」。

今天它们仍是两笔独立写入——一笔改本域的分组成员表，一笔走官方注册表的 `insertBefore`。两者存在两个不同的存储里，天然不能原子。

`DropTarget.mergeInto` 是留给合成写入的入口，**今天只有形状、没有调用方**。接上它的做法是：命中层在框与线同时落在一片上时改走它，宿主侧对应接口要在同一次调用里既写归属又写顺序。在那之前，这一类投放仍可能留下半个状态。

### 计划形状直接回答的三个问题

**「接不接」不需要全局判据。** 置顶区在「置顶会话的计划」里是一个 `rows` 档目标，在「工作区内会话的计划」里根本不在 `targets` 表里。跨容器投放不是「被禁止」，是「从未被计划」；跨插件拖拽同理——本包的计划若包含跨 cwd 目标，它的 `commit` 调外部插件的接口即可，不包含就不接。接纳规则的完整形态就是计划构造器这一个纯函数，可以单测，不需要任何静态范围声明或运行时放宽机制。

**原地投放（noop）大部分是构造期缺席。** 计划构造时不把自己的行、自己已在的容器收进 `targets`，命中层查不到即不标记、不提交。这一条不能靠提交期判等代替：归属没有变化时宿主仍会写一次盘。「把分组拖到自己的下一位」这类相邻 noop 由 `commit` 里的纯函数判出并返回 `undefined`（与官方 `sessionDragOrder` 返回 `undefined` 表示无变化同形），那是家族一与置顶段的路子；会话归组这一类没有位次，因此全靠构造期缺席。

**折叠段的换算有唯一归属。** `commit` 闭包在构造时绑定的是全量成员顺序（不是 DOM 里露出的行），落点只提供「参照行 id + 前后半」，换算在全量顺序上做：被折起的行不动，相对位置自动保持。等价于官方把「全量成员」与「折叠后渲染的行」拆成两个入参的取舍，这里是「闭包绑全量、锚点来自可见」。今天只有置顶段走这条换算。

## 落点检测只有一个入口

`data/dropSearcher.ts` 是检测当前落点的唯一 API。它**拿整棵树**，一次拖拽的名单由 `collectDropTargets` 从计划算出来（都是节点身份），收进 `maybeDropSearcher(tree, targets)`；此后检测只剩 `checkDrop` 一个调用：

```ts
const check = searcher.checkDrop(pointerElement, point, pointerNode)  // 三个都是身份，元素只用来量线的上下半
if (check.inside !== undefined) 在它那一格画一圈
if (check.order !== undefined) 在它那一格画一条线，side 给出上侧还是下侧
```

一次检测最多交回两个**节点**：一个画框、一个画线。落在哪个节点上由结果直接给出——调用方不再自己沿祖先链找区域，也不再把几格合并成一圈。

判定全在节点上做：

- **名单只回答「允许落到哪些节点上」，不回答「指针这一点属于谁」**。后者由 `chainOf(node)` 现算：从指针落着的那个节点出发沿树往上走（祖先工作区 → 它所在的那一片 → 它归属的分组 → 根节点），遇到的第一个在名单里的就是答案。组内任何一条成员行因此都能让罩着它的那一片响应，不必把成员逐一列进名单。
- **根节点那一片只在指针本来就落在 root 层时进链**。这不是给它一个「优先级最低」的特例——它压根不该在那条链上。无条件兜底会让组内换位、拖回自己那一片都多亮一圈「移出分组」的框。
- **框与线同源，都从链上取**。框由链上第一个能放进去的节点给出，不由 order 那一笔携带。早先它挂在 order 关系上、用**目标那一行**的祖先算，结果是：目标行有自己的 cwd 父工作区、而那个父工作区与来源毫无关系时，那一块会被无缘无故高亮起来。指针的问题只能由指针所在的那条链回答。
- **能进去的每一片，它顶层的成员都是位次参照**。跨虚拟分组的同层行因此也能谈先后：「移到那一行前后」与「移进那一片」本来就是同一件事的两半。反过来，祖先工作区不作位次参照——一个工作区既然已经确认自己要作为子工作区出现在某个容器里，它就不再与那个容器的行谈先后。
- **不碰 DOM 祖先链**。跨虚拟分组的两个工作区在 DOM 上互为祖先、在树上却不是父子；沿 `parentElement` 走会把「渲染细节」当成「结构关系」，这正是早先那一轮把框画错地方的根因。
- **框与线套多大由渲染层指名**，不由共同祖先去猜。**落点单位**是这一片能接住投放、框与线该套住的整个范围：分组把组头与组体圈成一块，工作区块把标题行与体内的子工作区、会话圈成一块。渲染层把它写在代表元素上（`data-wg-dnd-region`），计划用 `regionOf` 点名其中一格，命中层一次查回，不做「沿祖先链往上找到哪一层」的推断。
  - **落点单位是语义上的容器，不是指针恰好压着的那一格**。未归组段是工作区体内的一截，它自己不是容器：会话落到那里读作「回到这个工作区」，因此那一格与工作区标题行那一格共用同一个单位——整块工作区。若让它退回「这一格自己」，框会缩成那一段，而会话行与段内空白都读作同一次归属变更，同一件事就有了两个大小。
  - **一片只有一格时不挂标记**：它自己就是自己的单位（「只有一行的块」）。于是「只有一行」与「很多行」在机制层是同一件事，只是单位的元素不同。

旧的那一套（`findZone` / `resolveHit` / `targetOfZone` / `nearestRow` / `halfOf` 与合并格子的 `landingElements`）已删除：两条检测路径并存正是「画出的框与真正会写入的落点不是同一件事」的来源。

## 命中与标记不经过 React

拖拽期间的状态分两类，走两条路：

- **DOM 即时的**：够不着的压淡、当前落点标记、被拖行的画淡。压淡在 `beginDrag` 那一次写一遍、结束时清掉；落点标记在 `document` 的 `dragover` 里跟着指针写、移走时删掉；被拖行的画淡由行自己监听 `dragstart` / `dragend` 置本地状态。**整条拖拽路径零次 React 重渲染**——没有 context value 变化、没有穿透 memo 的问题。
- **提交时的**：`commit` 执行写入、拿回宿主快照、替换区域状态。这是业务本来就有的路径（`apply` 模式），与拖拽无关。

React 树与拖拽机制的唯一接口是 context 提供的一个稳定函数 `beginDrag(plan)`。提供者自身在拖拽期间也不重渲染——计划存 ref，监听挂 `document`。`data-wg-drop` / `data-wg-dnd-dim` 这类属性 React 从不渲染，因此 React 重渲染不会擦掉命中层写的标记；元素若在拖拽期间被卸载（折叠动画），最坏的代价是标记随元素消失，下一次 `dragover` 重新命中。

**order 的检测范围是整片，不是标题那一行。** 一条位次关系登记在 `workspaceHead/{id}` 与 `workspaceBody/{id}` 两格上，线跨整块工作区画在上下缘（计划用 `regionOf` 点名那一块）：指针停在体内的会话上时，读出的仍是「排在这个工作区之前 / 之后」，那一片与标题行是同一件事。只登记标题那一格会让体内成为死区，线也只有半截。

**平铺在 root 层的那一段也是位次参照。** 来源在某个虚拟分组里、目标平铺在 root 层时，两者既不并排也不同父，但「移到那一行的前后」是合法落点——落上去要同时做两件事：排到它前后，以及退出此刻所在的分组。后者由根节点那一片的 `inside` 关系给出，位次关系只补落盘的会话分组归属。两处都写 `moveToGroup('')` 会撞成两次写入。

一条容易漏掉的前提：**「按路径本来就是它的子工作区」不等于「已经嵌在里面」**。渲染层的嵌套要求两者同处一个虚拟分组（`nest.ts` 的 `inSameScope`），跨片的一对父子在界面上根本没有嵌在一起。因此落到祖先工作区体内的关系要再分一次：同片时是原地投放（不写），跨片时是把来源移进祖先所在的那一片（`moveWorkspace` 或 `nestInto`）。判漏这一层，框会照常画出来而松手什么都不发生。

**归入分组时同步虚拟分组归属。** 这一条是前一条的直接推论，但它的失效形态很隐蔽：归属落盘了，却因为父工作区与来源不同片而被 `deriveNesting` 当作无效数据丢掉，界面读作「进了分组但没进分组」。因此 `moveWorkspaceTo` 按「来源与目的地的差」把这一笔也写出来（见 `data/move.ts` 的 `planWorkspaceMove`）——它是这条交互的语义要求（用户把一行拖进另一片里的分组，要的是「这一行进到那一片去」），不是宿主需要提供的能力。

一个必须守住的边界：`commit` 闭包在 `dragstart` 时构造，绑定的是那一刻的数据。拖拽期间快照可能被别的 surface 改掉（新会话前插、别的客户端），因此带位次的写入一律在宿主侧复核锚点资格（锚点必须仍是目标层成员、不是来源自己），复核不过按无操作返回，不抛错。

### 三段渐进：压够不着的，只抬指针下那一处

拖拽期间用户要能回答两件事：这次能放哪、松开落在哪。三段按「只压够不着的」分开，而不是「点亮够得着的」：

1. **够不着的压淡**（`data-wg-dnd-dim`，`opacity: .45`）。判据是「这个元素自己的区域键不是落点，且它子树里也没有落点」——前者覆盖来源自己所在的那一片（按构造它不在计划里，拖回去是原地投放），后者让包着一片落点的外层退出（列表根节点罩着全部工作区，压它会把可投的目标一起压淡）。
2. **够得着的保持原样**。一次拖拽能落到的地方往往有好几处，逐个点亮会把界面涂成一片；反过来只让够不着的退下去，可投的那些不额外上色，读起来安静得多。
3. **指针下那一处抬高**（`data-wg-drop`），整块描一圈强调色边。

这是超过官方的引导强度——官方行拖拽只有落点线、没有区域引导——因此取舍上宁可克制：说「哪几处不行」比说「哪几处行」更少误报，也更少噪音。

**一份提交只画一圈。** 一份提交可以对应不止一格区域：分组块与它的分组头是两格，虚拟工作区分组的组头与组体也是两格。指针落在哪一格上用户看到的都是同一件事，各画一圈会被读成两个区域。因此绘制表按**区域键**存（`inside/<键>`、`order/<键>`），同一个键只服务一个元素；一片由好几格组成时由 `regionOf` 点名那一块，几格因此交出同一个元素。

早先按「共同祖先」合并格子（`landingElements`）的做法已删除：它要判「共同祖宗的子树里还有没有别的提交」，而分组非空时恒为真，圈永远退回组头那一小格，整块放入的框根本画不出来。改由渲染层指名之后这条闸门不再需要——画在哪一块是渲染层的事实，不是命中层从 DOM 结构猜出来的。

**画法的其余取舍**：`before` / `after` 是对某一条参照行的落点，标记因此画在那条行上，线才贴着它；「一格装多行」的段按锚点里的参照行 id 回溯到具体那一行，画在段容器上会让线落在整段的上边或下边。`inside` 是整块投放，画在合并后的那块区域上，整块描一圈——会话归组与移出分组用的是这一档，它们没有位次可言，因此不给位次的视觉。

**线跨整块，不缩到标题那一行。** `before` / `after` 表示「排在这一片之前 / 之后」，因此线必须横跨**整个区域**：一片可以装下别的行（虚拟分组含组内工作区、会话分组含组内会话、工作区块含子工作区与体内会话），只贴着标题那一行画会读成「落点只覆盖那一行」，宽度也跟着从整片缩成一行。

这一块就是这一片的**落点单位**：渲染层用 `data-wg-dnd-region` 把它写在代表元素上（工作区块写在整块的 `<section>`，虚拟分组写在分组容器，会话分组写在分组容器）。组头只是块里的第一行，直接拿它会把线画在组头下缘而不是整个分组的下缘。

**一处缝只画一条线，而且不从 DOM 里找。** 相邻两行之间只有一处空白，从上面靠近读作「排到上一条之后」，从下面靠近读作「排到下一条之前」——同一个插入位次，屏幕上却有两种画法：前者画在上一条的下缘，后者画在下一条的上缘，于是看起来是**两条**线，还各自带着 `after` / `before` 两种语义。

缝因此只由下一条代言：计划里点一句 `seam`（`DragPlanTarget.seamKey`，值是下一条那一格的绘制键），命中「之后」时改去取那一份「之前」，位置、标记、写入因此是同一件事。两种位置在界面上读数逐字相同，用户看不到自己是从哪一侧靠过来的。

两种「没有下一条」照常画在本条下缘：段尾没有下一条，或者下一条正是被拖走的那一条（那处是原地投放，线画上去只会跟着它一起淡掉）。

**行距归属于某一行，命中因此不需要几何兜底。** 相邻行之间没有 `margin`：那点间距挂在后一行**带**的上内边距里（`--wg-row-lead`，见 `layout-and-styling.md` 的行带一节），两条带严丝合缝，列表纵向的每一像素都落在某一条带上。指针停在原先那段缝里时，命中的就是后一条带本身，而它的前半段读作「排到它之前」。缝只由下一条代言这条规则因此落在真实元素上，不必再由命中层解一遍盒模型。

早先 `margin` 那套写法下这段空白不属于任何一行，按元素归属只能读到容器，用户把指针移进那 2px 里落点线就整个消失。当时的补法是让命中层按矩形倒推「指针上方最近的那一行」——那等于把一个纯样式参数变成运行时约定：行距改成别的值时那个上限值不会跟着变，也不会报错。行带改造之后这条补丁连同它的上限常量一起删除。
**线不画在压淡的那一块上，而是干脆不画。** 指针还停在被拖走的那一块上时，那一块自己带着 `.rowDragging`（`opacity: .4`），常常还整片压淡（`[data-wg-dnd-dim] { opacity: .45 }`）；两种不透明度按元素叠乘，画在它身上的线会被压成一条淡线，用户读到的不是「这里能放」而是「这条线的颜色不对」。因此绘制前查一次这一块是不是正淡着（自己或任一祖先带 `data-wg-dnd-dim` / `data-wg-dragging`），淡着就不给线——那种落点本来就是一次不改变结果的投放，画不画都不影响用户判断。

绘制表存的因此是**惰性的一格**而不是算好的元素：拖起那一刻 React 还没把画淡写到行上，落点得等到指针移动时才定。

**线用边框画，不用阴影或背景。** 三条理由各自都是实测出来的：

- 贴边的 `box-shadow` 只能贴着这一行自己的盒子。线要跨整片区域的宽度，缩进之后右边必然短一截；改成伪元素才能自己定左右缘。
- 2 CSS 像素落在设备像素网格的哪一侧由缩放决定（125% 下 2 × 1.25 = 2.5 设备像素）。浏览器对**边框**做设备像素吸附、对背景不做，用背景画会在不同缩放下显形为「不同落点的线粗细不一致」。按 dpr 1 / 1.25 / 1.5 / 2 各起一条浏览器量过，边框画法四档都干净。
- 线是浮层，必须带 `pointer-events: none`，否则它会吃掉行自己的点击。

**线画在行的盒子里，两端都不往外伸。** 这是一条同时管像素与命中位置的约束，两条失效形态都要单独说清：

- **外侧那一段会被裁掉。** 撑开体是 `overflow: hidden`，置顶区两档分别是 `auto` 与 `hidden`，列表是 `auto`——这些裁剪盒的上下缘正落在首末行的边上，伸出块外的线被**整条**吃掉，表现为「属性与命中全对而像素为空」。
- **外侧那一段也没有命中。** 线一旦画到行盒子之外，指针瞄着线就落在容器上，读出的不是这一行；于是**线在、松手却什么都不发生**。这一条比前一条更难发现：像素正常，只是拖不进去。

因此两端都收在盒子内侧：插到某行之前画在它的顶边（`top: 0`），插到某行之后画在它的底边（`bottom: 0`）。看得见的那一条与能放下去的是同一处，不必再靠外层容器让出上缘那一格。

早先「首行之前」画在 `top: -2px`、由容器补 `padding-top: 2px` 让出这一格。那一段留白确实能让线显形，但它在行盒子之外：列表根节点的像素问题解决了，命中问题反而被引进来——用户瞄着那条线松手，落点读成列表本身，提交为空。

线的左缘取行自己那一格缩进变量 `--wg-row-start`，与行的 `padding-left` 同源，因此线恒与文字左对齐，不必按层级写死像素值。

**根节点上两块分组之间的那道线**：根节点 `.list` 今天没有相邻兄弟间距规则，两块分组贴齐，该处线会压进上一块收尾 2px——已知退化，随根节点混排轮修。

### 拖到边缘时自己滚

长列表里换一个落点常常要滚很远，而原生拖放这条路把两件事都堵住了：

- **自带的边缘自动滚动太窄。** 实测（headless Chromium 154）指针距下缘 20px 处完全不滚，16px 才起步，4px 才到最快。用户实际停在哪个深度全凭手感，落在带外就一动不动。
- **滚轮根本不到页面。** 拖拽期间浏览器把滚轮吞在自己的拖放循环里，实测 DOM 收到的 `wheel` 事件为 **0**（静止时为 4）。这条与监听方式无关：不注册、`passive`、非 `passive` 三种写法读数一致。因此「让滚轮在拖拽中可用」在原生拖放之上无法实现，只能换掉整个手势层。

于是这一段由本包自己补：`beginDrag` 时起一轮 `requestAnimationFrame`，每帧按指针位置决定滚哪个容器、滚多少。触发带取 48px，速度随指针深入带内线性增长到 1000px/s——带宽与加速度都按「不用瞄准」定，这是相对原生那 16px 的主要改进。位移按帧时长算，帧率高低不改变手感。

**容器的挑选**：标了 `data-wg-dnd-scroll` 的容器里，取指针横向落在其左右缘之间、纵向落在触发带（或范围）内的那一个；同在其中时取文档序靠后的，嵌套容器因此先滚内层。横向必须判定——指针移到侧栏之外的会话区时，侧栏不该跟着滚。纵向则允许越出：把指针推到列表下缘之下是最常见的那一手。

两条排除规则：内容没超出一屏的不进来（没什么可滚）；`overflow: hidden` 的也不进来。后者是实测出来的坑——这种元素同样吃 `scrollTop`，滚它会把被裁掉的内容在**没有滚动条**的情况下推着走。置顶区展开档静止时正是这一种，它要浮出才变成可滚。

**滚动之后必须重算落点。** 程序化滚动不会重派 `dragover`（实测连续滚 6 次，事件数为 0，指针下的元素却已经换了），而 `pendingRef` 里存的还是滚之前那一格，照此提交会放进用户没看见的地方。因此滚动那一帧按同一个指针坐标用 `document.elementFromPoint` 重新命中一次。这条反查是这里的便利而非承重：jsdom 不实现它，取不到时跳过这一帧的重算，用例因此仍能在 node 环境下断言其余部分。

指针位置只从 `dragover` 里取。拖拽期间浏览器只保证派发拖放那一族事件，`mousemove` 在原生拖放中根本不产生，不能靠它。起拖到指针第一次移动之间有一段静止，那时还没有坐标，循环空转而不退出——退出就再也接不上。

这一段与引导的取舍一致，都不给可见提示：指针进了带就滚，理由和「只压够不着的」相同，多画一枚箭头或一层渐变会在拖拽的每一帧上都吵一次。

## 顺序持久化：两个存储家族

全部需要顺序的段按「有没有默认序」分成两个家族，各用一种存储。

### 家族一：归属数组兼顺序（无时间序语义的段）

会话分组列表、虚拟工作区列表、虚拟工作区成员——这些段没有「按时间排」的默认行为，数组序即界面序，渲染早已如此。缺的只是一个带位次的写入，各配一个宿主方法，回整份快照：

- `moveGroupBefore(workspaceId, groupId, beforeGroupId?)`——会话分组换位。
- `moveVirtualWorkspaceBefore(groupId, beforeGroupId?)`——虚拟工作区换位。
- **纯工作区的段不在这里。** 同层子工作区的换位、虚拟分组内顶层成员的换位、根节点平铺段的换位，三处的顺序持有者都是**官方注册表序**，写入口是官方的 `workspaces.insertBefore`，因此不占本包的存储。这一段的分野按「顺序持有者是谁」划，不按「读者看起来像不像一个段」划：一段需要本包单独存储，当且仅当该段成员含有宿主没有为之提供顺序原语的实体（分组、虚拟分组）。

存储不动、渲染不动。锚点资格在宿主侧复核（锚点是同层成员、不是来源自己），复核不过与「新顺序与现状逐位相同」都按无操作返回，不写盘。

### 家族二：独立顺序位 + 合成（有默认序的段）

置顶区在用户没拖过时必须保持官方集合的默认序（最近置顶在最前），拖过之后要切到手动序。在 `workspace_plus` 域的 global 槽位有一格：

```ts
orderSlots: Record<string, string[]>  // 段键 → 手动顺序，缺省表示该段按默认序
```

今天只有置顶区用这一格，段键是 `pinned`（`PINNED_SLOT_KEY`，与合成逻辑同处 `data/pinned.ts`）。宿主不解析这个键，只当一格存储用；把键的形状收在唯一消费方，是因为撤回会话排序之后只剩这一格用得到它。配套的语义：

- **接管**：用户第一次在置顶区完成锚点投放时，客户端把「落点换算后的全量新顺序」整份写入槽位。新顺序是从当时渲染序算出来的，接管瞬间显示零跳变——手动序从默认序里长出来，而不是替掉它。
- **渲染**：有槽位时按 `reconcilePinned(slot, entries)` 合成——槽位里仍是成员的按槽位序，不在槽位里的成员（新置顶的会话）按官方集合的位置接在后面，槽位里已不在成员集里的 id（取消置顶、归档）静默丢弃。没有槽位时按官方集合序，与引入这一格之前逐项相同。这与官方 `reconcileManualOrder` 的「保存顺序优先、其余按时间兜底」是同一取舍。
- **置顶段的两个消费者**：`pinned` 槽位只此一份顺序，置顶区按它渲染，分组内就地置顶段的名次（`pinRanks`）也从同一份合成结果取，两个表面因此永不打架。

**写入方法只需要一个半。** `setSegmentOrder(key, order)` 写一份槽位（空表即整格删除，同序不写盘）；`moveSession` 只改归属，不碰顺序位。

**清掉手动顺序的唯一入口在视图选项面板。** 手动序本身是用户意图，拖回去就是修正手段；「恢复」的价值只在「拖乱了想回到已知合理状态」，因此只留一个全局入口，不按段挂在行菜单上。它写的就是一个空表，与接管同一个方法：置顶区随即按 `reconcilePinned` 的「无槽位」分支渲染，回到官方集合序。这一条只在槽位非空时出现——没有可恢复的顺序时，摆一条点不动的行只会让用户去猜它为什么没用，而「哪些段手动排过」也不该靠菜单项的时有时无来表达。

### 会话段没有顺序位

会话排序（组内段内换位、跨段插入到指定位次、分组内就地置顶段排序）曾经与置顶区共用上面那一格，键分别是 `group/<workspaceId>/<groupId>` 与 `loose/<workspaceId>`。这一能力已撤回：**会话行拖拽只剩归组与移出两类归属变更**，段内没有位次可言。

逐类排查后找不到为段内手动排序辩护的用例：临时会话结束后即归档；长期重要的会话正是置顶集合的语义；「把一组相关会话按处理顺序排列」是分组的语义而不是顺序的语义；「本地重要但不够格进全局置顶区」的中间态得不到排序能给的持久性承诺（时间序随时把它冲走，除非整体接管）。

顺带消解的两个既有问题：

- **置顶边界可被混入。** 组内段曾是「手动序 + 默认序」的混合段，而拖拽机制对段一视同仁，非置顶会话可以被拖进置顶前缀里。撤回非置顶段的 `rows` 目标后，这条跨界路径在机制上不存在，不需要补运行时守卫。
- **整体接管的语义裂缝。** 整体接管把「手动排过的会话」与「未排过的会话」之间的相对关系留给实现猜，受害面现在收窄到置顶区——而置顶集合成员全是用户显式收录的，整体接管在那里不是裂缝而是正解。

旧数据不做正式迁移：撤回会话段排序时，拖拽功能尚未在生产环境中使用过，无需为旧键补守护或兼容代码。读取侧不再认这两类键，写入侧也不清理。

### 换算绑渲染序，不绑名单序

拖拽计划的 `commit` 闭包绑的是构造那一刻的**渲染序**（槽位与默认序合成后的结果），不是元数据里的名单序（官方 `pinnedSessionIds`）。名单序没有算上槽位，拿它换算会让「第一次拖拽接管」在当刻跳一下——而「接管零跳变」是可判的硬指标。

### 新建会话的位置

`createSessionIn` 只做归属变更：把新会话移进目标段（工作区行的 `+` 归入未归组段，分组行的 `+` 归入该分组）。它在段内的位置由默认序决定——宿主 `attachSession` 把新会话前插进段首，比较器也把空白会话排在普通会话之前，两条路径收敛到同一位置。撤回「新建会话锚点化」之后不需要再传锚点，因为没有段内位次可锚。

## 拖拽所有权

手势层在拖拽期间接管 `document`，而 `document` 是全局的。三处会撞上：侧边栏与对照 tab 双开、外部插件的原生拖放、页面上的其他拖放（拖文件、拖文本）。

所有权由模块级单例 `currentPlan` 表达，不需要锁协议：

- 只有 `beginDrag` 的调用方所在的提供者会挂 `document` 监听。双开时另一个实例的 `beginDrag` 没被调，它的监听不存在，天然不抢。
- 外部插件拖它自己的东西时不会调本包的 `beginDrag`，本包单例为空、监听不挂，互不干扰。反方向（本包拖、外部插件也挂了监听）由载荷前缀兜底：`dataTransfer` 写入 `wg-dnd:<sourceId>`，任何读到这个前缀的实现都知道这是本包的拖拽。
- 没有拖拽时 `document` 上没有任何监听，拖文件、拖文本完全不受影响。
- 浏览器本身保证同一时刻只有一场 HTML5 拖拽，单例因此不会并发冲突；防御性地让后到的 `beginDrag` 覆盖先到的即可。

## 性能边界：计划构造器的身份稳定

行级 `memo` 按引用比对 props，而拖拽计划的构造器会随归组上下文到达每一行。构造器的依赖若来自每次渲染新建的数据（布局返回的段数组、快照里的顺序位表、按置顶档位合成的比较器），构造器每渲染换一次引用，整片行的 memo 随之整片失效——绿灯测试无法证明身份稳定，这条代价只能靠探针量出来。

因此所有拖拽计划构造器遵守同一条规矩：**只用于换算与下发的数据放进 latest-ref，构造器在 `dragstart` 当刻读 ref，`useCallback` 的依赖列只留真正稳定的入口**（与 `ExpandableBody` 把节奏参数放进 ref 同一取舍）。身份稳定性由探针用例钉住（`test/pinnedDragMemo.test.tsx`）：无关重渲染后行拿到的计划构造器引用不变。探针的夹具必须与生产同形（动作面模块级共享），否则探针恒真，量不到这条机制。

## 全景工况的落点

「移动一个对象」拆成「移动什么 × 从哪来 × 到哪去 × 以什么位置落」之后，各工况的落点如下。每行独立可判。两个机制性前提：

- **官方的顺序有三套，彼此不通用。** 会话显示顺序在浏览器 `localStorage`（`sessionOrderByAccount`，官方 UI 拖拽走它）；工作区顺序在宿主落盘（`workspaces.insertBefore`）；会话在工作区内的 durable 顺序也在宿主落盘（`sessionIds` 数组），但官方 UI 从不读它——`reconcileManualOrder` 把成员列表当集合用，数组顺序当场丢弃。本表「写入」一列因此以本包的存储域为准，不套官方任何一套。
- **宿主那份数组会被别处改写。** 新建会话、分叉会话与 webhook 临时会话都经 `attachSession` 前插到 `sessionIds` 第一格；宿主写盘时的 prune 会 `filter` 剔除不匹配成员。既有成员的相对顺序不会被打乱，但第一格会被反复占走——这是「家族二」不把顺序写进宿主数组的直接原因。

| 工况 | 落点档 | 写入 |
| --- | --- | --- |
| 置顶区手动排序 | `rows`，`pinned` 一格区域、行带参照标记 | `pinned` 槽位 |
| 会话归组（含空分组） | `container`，分组头与整块分组两格 | `moveSession` |
| 会话移出分组（落未归组段） | `container`，未归组段那一格（来源在分组里时），落点单位是所在工作区块 | `moveSession` |
| 会话移出分组（落工作区标题行） | `container`，`workspaceHead` 那一格，落点单位同上是所在工作区块 | `moveSession` |
| 会话分组之间排序 | `rows`，分组头一格一行 | `moveGroupBefore` |
| 虚拟工作区之间排序 | `rows`，分组头一格一行 | `moveVirtualWorkspaceBefore` |
| 工作区移入 / 移出虚拟工作区 | `container`，组头 + 组体 + 组内每行；移出落 `root` 与根节点平铺行 | `moveWorkspace` |
| 工作区在虚拟工作区内排序 | `rows`，同层工作区行一格一行 | 官方 `insertBefore` |
| 子工作区移入 / 移出会话分组 | `container`，祖先工作区体内的分组头；移出落父工作区行 | `nestWorkspaces` / `unnestWorkspaces`；跨片时先 `moveWorkspace` 到目标那一片 |
| 折叠段的落点换算 | 锚点来自可见行，换算在全量成员顺序上做 | 与对应段同一写入 |
| 拖到段尾 / 空段 | 段内空白读作 `inside`，追加到段尾 | 与参照行同一写入 |

会话行自己**不带区域键**（只带可拖属性），因此落在组内任意一行上时命中层会一路向上走到包着它的容器那一格。这正是「拖到组内某一行上读作归组」成立的原因；若给会话行挂一格不进计划的键，那一行就会变成命中层停下的死区。工作区的标题行相反：它自己带一格 `workspaceHead`（工作区排序要按它算前后半），因此会话计划里必须**显式登记同一格别名**——目录性质的落点，拖到它上面与拖到未归组段那一格上是同一件事。

同一个区域键在不同计划里可以配不同档（分组头在会话计划里是 `container`、在分组排序计划里是 `rows`）；但在**同一次**计划里一个键只能有一档。工作区计划里父工作区行可能同时够到「同层换位参照行」与「移出会话分组落点」两档，构造期让它先让开 `rows`、只留 `container`——两条读法都成立时，解除嵌套是用户看得见的那一层变化。

### 明确不做的

| 工况 | 理由 |
| --- | --- |
| 平铺视图（flat）下排序 | 平铺的语义是时间序单列表，成员不属于任何容器，顺序没有落点；用户切到平铺态就是想按时间看。平铺态的行不挂 `draggable` |
| 未分组桶（stray）内排序 | 桶里是不属于任何工作区的会话，在剩余里手动排序语义价值低，与时间序默认预期冲突。处理同上 |
| 多选拖拽 | 产品里不存在多选，为它设计载荷形状是无锚点的过度设计 |
| 触屏拖拽 | 原生拖放没有触屏支持；架构上手势层是独立一层，计划层不知道下面是原生还是自绘，触屏需求真实出现时换手势层即可 |
| 拖拽中实时重排预览 | 落点标记已能回答「放开落在哪」；实时重排把折叠换算成本从提交一次变成每帧一次。机制层不挡它——`commit` 是纯函数换算，做预览时同一份换算在 `dragover` 里喂给渲染即可 |
| 键盘可达的排序 | 菜单移动是既有的键盘路径，覆盖归组；排序的键盘路径等真实需求出现时再评 |
| 会话段内手动排序 | 已撤回：只能归组与移出，不能调整会话在段内的位次。置顶区的手动排序保留，理由与复活条件见上文 |
| 悬停自动展开折叠段 | 展开会改变命中几何（行突然出现、指针下的元素移位），需要实测手感。折叠段只能整块 `inside` 投放（分组头仍在 DOM 里） |
| 拖拽中用滚轮翻列表 | 滚轮事件在原生拖放期间被浏览器吞掉，页面收不到，只能在手势层换成自绘才拿得回来。边缘自动滚动已覆盖「翻到列表另一头」这个需求 |

## 方案空间与取舍

同一套需求有几条不同的实现路径。本节按「选这条路的代价与坑、什么信号出现时值得换过去」逐条记录，供后续迭代对照——判据是「读起来应不应该换成那条路」，与本文描述的实现是否沿这条路走过来无关。

### 能力注册表（备选）

每个有序段注册一个能力对象：`accepts(source)`、`resolve(point, source)`、`commit(source, anchor)`，提供者维护注册表替代 DOM 标记。它的知识归属是对的——注册粒度在段，段手里正有全量成员顺序。

代价：注册表要自己维护层级、顺序与卸载，而 DOM 的层级是免费的（段与段的嵌套在 DOM 里天然成立，注册表里要手动表达「先问内层」）；命中测试从「查一张静态表」变成「问一圈注册对象」；机制层从纯函数变成带生命周期管理的 hook，验证成本跟着涨。

换过去的信号：段的数量与类别膨胀到「计划构造时要枚举的目标集」比「段各自声明能力」更难维护，或需要在拖拽中段与段之间动态协商。

### 意图总线（备选）

拖拽载荷即业务意图（`{ kind: 'reorderSession', ... }`），放开后由一张可组合的提交器分派表处理，外部插件往表里注册自己的提交器。它把「新增一个工况」摊平成「加一档意图 + 注册一个提交器」，提供者零改动，跨插件拖拽的事件所有权与接收也由同一张表自然回答。

代价：抽象层级最高——意图联合要前瞻性地覆盖全部工况，漏一个就要改联合，而联合一改所有提交器的 `switch` 都要跟着补。参与跨插件拖拽的插件只有一个假想对象时，为它引入整套意图层是过度设计；计划的 `commit` 本来就是「意图 + 执行」的闭包形态，核心价值已经覆盖，只是不经过全局分派表。

换过去的信号：参与跨插件拖拽的插件多到一个点一个 `commit` 目标维护不动，需要统一的提交器分派表。

### 自绘指针拖拽（被否）

`pointerdown` 起拖、全程自绘。否掉的三条理由：行本来可点（点开会话），自绘要在 `pointerdown` 与 `click` 之间加位移阈值与计时器来区分点与拖，而原生拖放浏览器已经分好；容器边缘自动滚动浏览器自带，自绘要另写；jsdom 不实现 `elementFromPoint()` 与 `setPointerCapture()`，命中与捕获在用例里只能靠替身，验证力反而更弱。

第三条需要订正：浏览器自带的那段自动滚动只有贴着边缘十几像素宽，滚轮在拖拽期间又被吞掉，因此**两条路都得自己写滚动**。它仍不足以支持换成自绘——自绘要赔上区分点与拖的整套时序，而滚动这一段在原生路径上加一轮 `requestAnimationFrame` 就够了（见「拖到边缘时自己滚」）。真正值得换过去的信号是滚轮：那是浏览器在原生拖放里不给的能力，只有自绘才拿得回来。

### 区域声明 `accepts`（被否）

「接不接」由区域声明（静态 scope 属性或动态回调）。否掉：这个知识长在拖拽的发起方，让区域各自声明会把一条规则拆散到所有区域上；静态 scope 表达不了「置顶区接会话但只在置顶计划里」，动态回调则让「这个区域为什么没亮」的排查从看 DOM 变成断点回调。计划驱动把整张接纳表集中在计划构造器一处，可以用纯函数单测。

### 会话段直接改渲染为数组序、不设顺序位（被否）

否掉（当时）：所有既有分组的 `sessionIds` 是历史插入序，渲染从时间序跳变成插入序是用户可见的无故变化；且「创建顺序」与「手动顺序」无法区分后，「恢复时间序」永远不可能。槽位方案的接管是渐进的（第一次拖拽才冻结），且无槽位的旧数据零迁移成本。

这一条随会话排序的撤回而失效——会话段现在**就是**按默认序渲染，槽位只剩置顶区一格。

### 顺序放浏览器 localStorage（被否，官方做法）

官方把 `sessionOrderByAccount` 放 view store 落 `localStorage`。否掉：本包已有 durable 的 `workspace_plus` 域，同一语义存两处会产生「本地与落盘不一致以谁为准」的问题。代价与官方不同——本包的顺序跨设备存活。

### 顺序写宿主 `sessionIds`（被否）

否掉：新会话前插（`attachSession`、webhook 临时会话）会反复顶掉手动位置，且官方 UI 自己都不读这份顺序。槽位机制让置顶段与（撤回前的）会话段都不需要碰宿主数组。

| 命中层自己画出的落点 | `scripts/probes/drag-drop-marks.mjs`（真实浏览器） | 挂真实的 `WorkspaceGroupsRegion`，用 CDP 拖拽拦截制造原生拖拽，让命中层自己画标记，再量标记与像素：一处缝一条线、线画在整块上而不是缩在行上、线在盒子内、横跨整块宽、不在压淡的块上、指针停在压淡区时不出标记 |

jsdom 不做布局（`getBoundingClientRect()` 恒为零矩形）也不实现 `DataTransfer`，DOM 用例因此显式替身参照行的矩形带与最小 `dataTransfer`，前后半由用例摆出的高度差算出确定读数。会话归组全走整块档，落点不再需要摆高度，只有给分组排序与置顶排序的用例仍要替身矩形带。

**落点线的四个历史缺陷只能在这里量。** 线被裁剪盒吃掉、线画进容器内边距（看得见但指针命中不到）、同一处缝两条线、线画在被拖淡的那一块上——四条都长成「属性与命中全对而像素不对」的样子，jsdom 里一条都观察不到，这也是那批 DOM 用例通过却编码了错误前提的原因。`scripts/probes/drop-line.mjs` 因此不验具体某个位置，而是对每个候选元素逐一写标记、截图、数像素，四个不变量一起查。它的价值在能红：把 `top: 0` 改回 `-2px` 会报 11 处，把 `right: 4px` 改成 `right: 60%` 会报 25 处，给标记元素加一层压淡会报满页。

**「标记挂在哪个元素上」与「线画在哪个像素上」是两半，由不同的东西守着。** 前一半由 jsdom 用例守（`test/orderDom.test.tsx` 里三条会因 `paintFor` 的格子优先级被破坏而红）；后一半由 `drag-drop-marks.mjs` 守，它挂真实组件、让命中层自己画，再量像素。

`drag-drop-marks.mjs` 的判据有一条是「线必须画在带区域键的整块上，不能缩在行自己身上」。注入破坏验证过它能红：把 `applyHit` 改成「标记一律画在指针落着的那个元素上」，它报出「线画在行上（`SPAN.rows_headSurface`），而不是它所属的整块」——这正是历史缺陷「线缩到标题那一行」的形态，而 jsdom 在那个形态下属性与命中都还是对的，抓不到。

它也不覆盖 `paintFor` 里「优先指针那一格」那条分支：本页面的场景中指针所在格恒等于该节点的第一格，破坏那一条探针输出不变。那一条由 jsdom 用例负责。

写这类探针时最花时间的不是判据，是把它们写对。这一份先后把三件事误判成代码缺陷：`inside` 框的 inset 描边被数成第二条线；用启动时取的行矩形去算起拖坐标，而 React 重排后那个坐标落在了会话行上（拖拽计划因此是会话而不是工作区）；指针停在压淡区上本来就没有标记。前两条靠取证元素链发现，第三条靠把「压淡区无标记」写成设计。

## 诊断日志

拖拽的失败模式大多**在界面上看不出异常**：落点画对了、松手却没写入；写入发了、宿主持有的分组列表里却没有那一项。这类问题靠观察界面无法定位，只能看链路上每一步的现场。因此机制层与服务层各留了几处诊断日志。

打开方式三选一：

- 浏览器控制台执行 `__workspacePlusDebug()`，当场生效，不必刷新
- 浏览器控制台执行 `localStorage.setItem('workspace-plus:debug', '1')` 之后刷新，跨会话保持
- 宿主启动时设置环境变量 `WORKSPACE_PLUS_DEBUG=1`

关掉用 `__workspacePlusDebug(false)`，它同时清掉 localStorage 那一格。

日志只打在**决策点**，不逐帧打。指针每移动一像素都会重算落点，逐帧打会把真正要看的那几行淹掉，因此 `hit` 只在落点摘要变化时才输出。

日志分两级，关键在于哪一些**不受开关管**：

| 级别 | 位置 | 打什么 |
| --- | --- | --- |
| 常开 | 浏览器 | `drag begin`：被拖的来源、计划里有哪些格、其中多少格在 DOM 上真的找到了元素、几块被压淡 |
| 常开 | 浏览器 | `commit`：松手时提交的框与线 |
| 常开 | 浏览器 | `snapshot applied`：宿主回来的那份分组状态 |
| 常开 | 浏览器 | `drop with no landing`：松手时没有任何落点 |
| 常开 | 浏览器 | `group change failed`：写入被宿主拒绝 |
| 常开 | 终端 | `moveWorkspace 写入完成`：写的是哪个工作区、写进哪个分组、写完之后各分组的成员 |
| 常开 | 终端 | `moveWorkspace 拒绝写入，分组不存在`：客户端拿了一个服务端已经没有的分组 id |
| 开关 | 浏览器 | `hit`：指针坐标、指针落着的格、命中的节点、框与线各指向谁、画出来的标记 |

前三行是链路骨架：缺一条就说明那一步根本没执行，这比任何内容都先要看。后五行是「本该落下去却没落下」的分叉，写入被拒绝而界面已经画过落点，用户看到的就是「拖了没反应」。它们都不能依赖用户事先打开什么开关，否则故障现场什么都不留。

**宿主侧这几条用 `error` 级别而不是 `warn`。** cordis 的 exporter 按「阈值 < 级别就丢弃」过滤，`warn` 的级别是 2、默认阈值是 1，因此 `warn` 在多数配置下根本不会输出；`error` 是 0，任何默认配置都能看到。这条判断是从 cordis 的 `LoggerLevel` 与 `_method` 的实现里读出来的，不是猜的。

一次正常拖拽的日志大致长这样：

```
[workspace-plus] drag begin source=kind=workspace id=ws-3 targets=[virtualWorkspaceHead/wg-1|virtualWorkspaceBody/wg-1|workspaceHead/ws-1|...] painted=16 dimmed=3
[workspace-plus] hit pointer=x=120 y=81 pointerZone=workspaceHead/ws-2 node=workspace/ws-2 check=inside=virtual/wg-1 order=workspace/ws-2 side=before marks=inside@div[virtualBlock/wg-1] before@section[workspaceBlock/ws-2]
[workspace-plus] commit inside=virtual/wg-1 order=workspace/ws-2 side=before
[workspace-plus] snapshot applied groups=[wg-1[ws-2]]
```

`drag begin` 那行里的 `painted` 与 `targets` 两个数对不上时，"界面有格、计划没有"或反过来就是这一次拖拽的问题所在；`targets` 里没有你想落的那个分组，说明计划构造那一刻的数据里它还不存在。
