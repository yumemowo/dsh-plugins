同一棵树（三条会话已置顶，分布在三个不同深度：工作区未归组段、工作区分组内、深层子工作区的分组内）， 九个方案并排。每列都是完整视口高的侧边栏复刻：280px 宽（官方 clampWidth 的默认档）， 含实现里的区域 header（两行标题 + 搜索槽 + 三个 28px 入口）、行高、缩进公式、引导线、色阶， 指示器按落地版绝对定位在行最左缘。 九列的元素完全相同，只有置顶的呈现方式不同，因此可以直接横向比对。

负空间：侧栏里工作区区域的上方与下方还叠着其他插件的槽位，用顶部两个滑块模拟。 斜纹暖色块不属于侧边栏内容，只占位，用来观察列表可视高度被挤到多少。

与实现的对齐：影响布局的部分按已落地实现取值，不是原始设计稿的取值。 九列并排是为了选型，只有 ⑥（置顶面板，悬停展开）那一列的取值与实现逐项相同： 段头高 30px、左缘 8px、箭头 16px 槽里放 14px 字形且排在名字之前、 行尾提示 12px、行距 2px、行尾统一为「时间 → 操作位 → 图钉」、 图钉 16px（未置顶时连宽度一起收掉）、字形取官方的 IconPinOutlineRegular / IconPinFillRegular、颜色取 caption 档。 顶部「置顶区区分」默认停在实现采纳的「区域级标题 + 空白区分」那一档。 页面末尾的 #measure 里有一组「段落几何」断言逐条核对这几项。

九个方案

#做法置顶升到哪一层折叠后还看得见吗新增常驻高度
①现状（无置顶）——0
②就地置顶它所在的那一段（会话分组内 / 工作区未归组段内）看不见0
③工作区顶置顶所属工作区的顶，跨出会话分组看不见0
④区域顶合成段区域的顶，跨出工作区看得见有（随置顶条数增长）
⑤④ + 置顶区定高滚动同④看得见有（恒定 5 条）
⑥置顶面板（悬停展开）同④看得见有（恒定 5 条，指针进入时浮出）
⑦置顶面板（点击展开）同④看得见同⑥，触发改为点击
⑧就地置顶 + 折叠透出同②看得见（带路径）0
⑨就地置顶 + 折叠计数同②看得到「有」，看不到「是什么」0

①~③ 与 ⑧⑨ 都不给置顶新建常驻区域，差别只在置顶行落在哪一层、以及折叠时要不要把它透出来。 ④ 是唯一新增常驻一段内容的方案，也是唯一在收起态仍然看得见置顶标的方案；⑤⑥⑦ 在它之上把段高封顶。 ⑦⑧⑨ 只作对照，最终不采用（理由见设计过程）。

三个约束

  • 垂直空间已经是负资产。区域上方已叠着四个其他插件的槽位，区域自己的 header 在宽栏是两行标题加四个入口。 任何常驻的一段都要从列表可视高度里扣——这是④的主要代价，用上面那两个滑块可以现场看到被挤到多少。
  • 「用户显式折叠优先」是本包既有不变量（见 数据存储）。 「置顶了就自动展开祖先容器」这条不能用，能走的只有「折叠容器把置顶行透出来」，即⑤⑥。
  • 「置顶」这个词已被选择器面板占用（管根节点条目的排序）。会话置顶进来后同屏会有两个不同作用域的「置顶」， 必须先决定是统一成一个概念还是刻意分开命名。

②③ 的共同代价：会话分组被自我否定

② 把置顶行升到「它所在那一段」的顶。若那一段是用户自己建的会话分组，置顶就在分组内部重排，分组语义保住。

③ 再往上抬一层，置顶行会跨出它所在的会话分组。这不是排版差异，而是语义取舍：用户建分组就是为了「我把它放这儿」， ③ 等于让置顶覆盖这个意图。③ 用左侧一条短竖线标出「它其实在别处」，但那条线只说明发生了脱组，说明不了它原来在哪， 因此这一段的行尾还要补上来源路径。

③ 还有一处必须先定死的范围：它只提本工作区名下的置顶，不递归进子工作区。子工作区有自己的顶， 它名下的置顶由它自己那道工作区行承担。若递归进去，深层子工作区里的一条会被每一层祖先各提一次，同一个标题在屏幕上出现多遍。

提走与摘除必须成套

③ 与 ④ 都把行提到别处，因此原位要把它们摘掉。只提不摘会让同一条会话在屏幕上出现两次—— 原分组里一次、提上去的那一段一次，那不是置顶而是复制。对照稿把这条收在一处分派（sessionsRunInPlace）里， 工作区层与会话分组层两处渲染都走它，因此不会出现「有一处忘了摘」。

④ 的实测几何

④ 的合成段落在列表最前，段头与它的行都从 24px 起——与一条深度 0 的会话行同列。 这一格不能省：指示器是 16px 宽的绝对定位盒，内缩 6px 后占 6–22px， 行内左缘不到 24px 时它会压在标题上（对照稿早先的版本就是这样）。

这一段随内容滚动，不给它固定高度；代价是纵向位置上它占的是列表第一屏，置顶一多，最先看到的就是置顶而不是最近用的那个工作区。

⑤ 的实测几何

⑤ 的幽灵行缩进跟它原本所在的那一段走（未归组段 24 + 16d、会话分组内 40 + 16d）， 因此标题左缘与它替换掉的那一行完全一致。按对照稿样式实测（相对列表左缘）：

收起的容器原本所在段幽灵行标题展开态真实行标题
工作区 dsh_plugins（d=1）未归组段4444
子工作区 packages（d=2）会话分组内7676
会话分组 工作区侧栏（d=1）会话分组内6060

三档都对齐，但这条结论依赖两个细节，写错任一处幽灵行都会与真实行错开一格：档位不是「折叠的是工作区还是分组」， 而是「这一行原本在容器的哪一段」；深度也继承不到——幽灵段渲染在折叠容器之外，--wg-depth 与档位 都得由每条幽灵行自己带上。

另有选择器上的一处静默失效：幽灵段渲染在容器之后（容器收起时 .wsBody / .groupBody 根本不渲染）， 因此缩进档位不能写成 .wsBody > .ghostRun——那条选择器永远不匹配，padding-left 退回 0， 幽灵行整段贴到最左缘，且控制台没有任何报错。

幽灵行右侧补一个来源路径，说明它来自哪个折叠的容器。这是 ⑤ 唯一的空间代价： 路径标签占的正是行尾相对时间那一格，两者在同一行里不能并存。

⑥ 的计数与分组行的会话数会粘成一个数

⑥ 把置顶条数放在折叠容器行尾，而复用「会话数 / 工作区数」那一槽的行尾已经有一个裸数字。 两个裸数字并排会被读成一个数（3 与 1 读成 31）。 对照稿给置顶计数加了一枚胶囊底，把它读成一枚独立的标记。

置顶标记的三种画法

行首那一格已经没有了。指示器落地时改成了绝对定位在行最左缘（见 会话行指示器的备选方案）， 因此置顶标记不能像官方那样占行首图标列，只能往行尾或段头走。

画法落点代价
行尾图钉行内，排在时间之前与行尾时间争同一格；行悬停时让位给操作位，图钉会跟着消失
小区段头「置顶」置顶段之上、占一整行每多一段就多 22px；只在置顶行连续成段时才成立
不标—零成本；置顶行与普通行完全同形，只能靠位置推断

顶部那个下拉可以现场切这三档。

与状态底色、选中态的优先级

置顶行不引入新的底色。状态底色（运行 / 待交互）与选中加深都已占用 background-color， 见 布局与样式对齐。 置顶是位置事实，靠排序与（可选的）标记表达，不再叠一层颜色——叠上去会与状态色互相稀释， 而状态是当前正在发生的事，优先级高于「我收藏过它」。

平铺展示方式

平铺下没有容器，②③⑤⑥ 全部退化成同一件事——置顶行排到列表最前，方案之间的差别归零。 ④ 更是完全失去意义：它合成的段与平铺列表本身同形。 因此平铺这一档只说明一件事：别为了让平铺也分得开而在平铺里再叠一层置顶段。

采用的方案

基座取 ②，把「顶」定在所在会话分组的顶：保住分组语义，置顶不覆盖用户显式建的结构； 零新增常驻区域、零命名冲突、零与既有折叠约定的冲突；与官方同构，语义上不需要额外解释。

「埋得深」当独立问题解，用 ⑥ 的轻量版（折叠行尾的置顶计数 + 直达）。这样 ② 唯一的缺点被补掉， 且不碰「显式折叠优先」那条不变量。⑤ 的带路径透出更精确，但它占掉行尾时间那一格， 且会在折叠容器下面再长出一段内容，视觉噪音高于收益，因此不作为基座、只作为 ⑥ 不够用时的备选。

不做常驻的全局置顶区（④）。理由三条：垂直空间已经是负资产；与选择器的「置顶」同名冲突； 全局平铺与本包「分得开」的主张相抵。若最终一定要全局，只接受零常驻高度的形态（选择器的置顶分区或 header 浮层）， 不要插在 header 与列表之间——那会隔断标题第二行「当前聚焦对象」与它下面那片列表的视觉连接。

尚未决定

  • 会话置顶与选择器的根节点置顶是一个概念还是两个，文案与图标要不要区分。
  • 置顶标记的最终画法（上面三选一），以及与状态底色、选中态的优先级。
  • 归档会话、空白会话能不能置顶；会话在分组间移动后置顶归属怎么走。
  • 置顶条数上限——不做上限时，置顶一多就会把列表挤没。
  • 置顶之间怎么排序：按置顶时刻、按最近使用，还是允许手动拖动。
  • 置顶是否需要跨端同步（本包的 picker.pinned 走宿主存储域，而会话置顶若不落盘则只在本浏览器有效）。
