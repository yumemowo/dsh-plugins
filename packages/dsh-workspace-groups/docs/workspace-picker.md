# 工作区选择器：本轮迭代的依据文档

本文记录 header「工作区选择器」这一轮迭代的**依据**：需求条目如何落成设计决策、
每条决策为什么这样选、哪些结论是实测出来的、以及验证方式。它同时充当两条用途——
后续改动这个功能时先读这里，以及这套做法在别处复用时的参考。

本文只讲这一轮。既有功能的完整交互细节见
[交互细节与官方对齐依据](ui-details.md)，存储结构见 [数据存储](data-storage.md)。

的选项往往才是后来者最容易重走的那条路。

## 三个需要用户拍板的分叉

以下三处没有唯一正解，按仓库「发现疑惑点先抛出」的约定问过用户后才实现。记在这里
是为了让后来的改动知道**当前取舍是选出来的，不是唯一的**。

### 菜单列到哪一层

只列根节点单元格，而不是「全部工作区（含组内的）」或「平铺全部工作区」。理由：聚焦
组内某个工作区与聚焦它所属的分组看到的是同一片内容，多列一遍会让菜单长出与列表层级
重复的一层。聚焦到分组后仍可再聚焦组内某个工作区——那时它已经是根节点单元格了。

被否掉的替代方案是「列出全部工作区，分组名作为分组标题」：任何工作区都能一步聚焦，
代价是菜单更长、选组内工作区时还要同时决定列表形态。

### 聚焦分组时要不要保留组头

**不保留。** 第二行已经写着组名，根节点那层再渲染一次就是同一个名字并排出现两次。
因此 `focusedLayout` 对分组聚焦交出 `{ groups: [], loose: 组内工作区 }`。

被否掉的替代方案是「保留组头（仍可折叠）」：组内工作区还能整组收起，代价是组名出现
两次，而且那个组头的折叠状态与「聚焦」这一层状态会互相打岔。

### 行结构与工作区行同形

条目行是 `role="button"` 的 div，三枚 16px 操作按钮嵌在行内的操作位里——与
`WorkspaceRow` 同一套结构、同一套 CSS 规则（`.wg-row` / `.wg-row-actions` /
`.wg-row-action`），因此两处看起来、点起来一致，显隐语义也不可能各自漂移。

**行用 div 而不是 `<button>`，就是为了按钮能嵌进去**：按钮不能嵌按钮。第一版把行
做成 `<button>`、三枚按钮做成它的兄弟节点，结果是「行 + 三个并排热区」——行的可点区
比看起来窄，悬停高亮也只盖住行那一截。键盘激活改由 `handleRowKeyDown` 承担，与
工作区行同一套。

被否掉的替代方案是「把这三件事收进条目自己的 `...` 子菜单」：与列表里的行菜单一致，
但下一级面板又要多一次悬停，而这三件事恰恰是**在浏览菜单时顺手做**的。

被否掉的替代方案是「把这三件事收进条目自己的 `...` 子菜单」：与列表里的行菜单一致，
但下一级面板又要多一次悬停，而这三件事恰恰是**在浏览菜单时顺手做**的。

### 「切换到新工作区」为什么要有

新建的分组追加在列表最末。用户若正聚焦在某一片内容上（比如某个工作区分组内部），
建完分组后新分组落在当前视野之外——界面上就是「点了确定但什么都没变」。勾上这个
选项就在建完之后把视图切过去。

**它只在已聚焦时出现**：正看着「全部工作区」时新分组本来就在视野里，没有可切的目的地，
给一个勾了也无事可做的选项只会让人以为它有什么作用。改名时不出现（改名不新建东西）。

### 置顶怎么放进去

**挂在条目行尾的按钮，只在该行悬停或它自己拿到键盘焦点时出现。** 它与菜单项是两个
按钮：行本身是「去这个工作区」，行尾是「把它固定住」。合成一个热区会让「想置顶却
跳走了」。已置顶的那一枚常驻可见——它是这条记录当前的状态，不该只在悬停时才读得到。

被否掉的替代方案是「工作区行 `...` 菜单里加一项」：与既有行菜单一致，但要多点两层
才能置顶，而置顶恰恰是「在浏览菜单时顺手做的事」。

## 设计要点

### 三条状态记录，只有一处变换逻辑

聚焦 / 最近使用 / 置顶三份记录的形状与全部纯变换放在 `src/pickerState.ts`，**宿主
半边与浏览器半边共用**。宿主在删除工作区或分组时用它修剪，浏览器半边在渲染菜单时用
它排序，两边因此不可能各写一份「最近使用怎么排」的判断。

条目键自带类别前缀（`src/rootEntry.ts` 的 `ws:` / `vw:`）：工作区与工作区分组的 id
由不同生成器产出，但仍可能撞值，只存 id 会让一条记录在两种含义之间摇摆。

### 为什么记录比展示长

`recent` 存 20 条（`RECENT_HISTORY_LIMIT`），菜单只展示 5 条（`RECENT_SHOWN`）。
若只留展示用的那 5 条，第 6 次之后用过的条目在置顶区里就彼此「一样近」——置顶区要求
按最近使用排序，而排序需要的信息比展示需要的多。

### 「记录比事实活得久」的两条防线

三份记录是**唯一一处会指向已不存在对象**的地方：工作区被删、分组被解散之后，那个键
仍会留在记录里。两道防线：

1. **宿主在删除时一并摘掉**（`forgetWorkspace` / `deleteVirtualWorkspace` 走
   `dropEntry`，与清理归属记录合成一次 global 写入）。否则「对象已消失、聚焦还指着
   它」会有一段可观察的窗口。
2. **渲染菜单的那一侧再过滤一次**（`resolveFocus` / `pickerSections`）。即使记录被
   手改过，也不会渲染出指向不存在对象的条目。

聚焦的键解析不到时**退回「全部」而不是渲染空列表**。这一条是写测试时发现的真实缺陷：
按一个失效的键过滤会让列表整片空掉，而第二行还写着一个已经不存在的名字。修法是让
「聚焦解析」「第二行文案」「列表切分」三处共用同一个 `resolveFocus`。

### 自绘菜单的边界：抄约定，不抄结构

官方 `Menu` 原语的条目只有「前导图标 → 文案 → 尾部选中标记」三个槽，**没有可折叠的
分区头**，也没有挂在条目行尾的第二个按钮。两条需求都落不进那个形状，因此面板自绘。

但**外观与交互约定照原语取**：落点贴触发器下缘、放不下翻到上方、两个方向都夹进窗口
（边距 12px / 缝隙 4px，与原语同值）、指针离开后延迟 200ms 关闭、`Escape` 关闭并把
焦点还给触发器、方向键在条目间移动。

那条 200ms 延迟不是随手取的：触发器与面板之间隔着一道 4px 缝隙，指针从前者移向后者
时会先离开触发器。不留这段延迟，用户还没点到条目菜单就没了——与官方原语同一个理由。

### 无障碍是展开式弹出层，不是 `role="menu"`

面板里既有可折叠的分区头，也有行尾那枚置顶按钮，而 `role="menu"` 只允许 `menuitem`
一类的子项，两者都塞不进那个模型。因此面板取 `role="group"`，两个触发器都只声明
`aria-expanded`（**不写 `aria-haspopup`**——那等于承诺一个 `menu` 角色）。

第二行的可见文字只是一个工作区名，因此它另有一个「切换工作区：{name}」的无障碍标签：
只报名字的话，读屏听上去那是一段说明文字而不是一个入口。

### 搜索展开时面板收起

搜索展开时标题整块让位（两行都收拢淡出，指针事件也一并关掉）。面板若还开着，就悬在
一片与它无关的结果列表上——它的两个触发器此刻都不可点。因此面板的 `open` 与搜索态
相与，搜索一开始它就收起。

### 为什么两行合起来是一个按钮

两行表达的是同一件事（当前在看哪个工作区，点开可以换一个）。分成两个可点区域只是
把「点上面还是点下面」变成一个问题让用户去试，而两次点击的后果完全相同。因此整个
标题块是一个按钮，箭头只是它自己的开合指示——无障碍上因此只有一处 `aria-expanded`，
标签是「切换工作区：{当前聚焦的对象}」。

被否掉的替代方案是「第一行 + 箭头一个按钮，第二行另一个按钮」：焦点落在第二行时少
一步（最近的可点区域就是它在说的那个对象），代价是同一件事有两个热区、两处
`aria-expanded` 需要保持一致，而收益只是省下鼠标上移 20px。

## 实测记录

以下几条不是推导出来的，是量出来的。按仓库约定，界面几何与性能结论**必须有同
harness 实测**，不得以静态阅读推断。

### 图钉必须斜着画

第一版画的是正向图钉（钉帽水平、钉子竖直），16px 下读成**过滤器**——钉帽那条横线
加向下收拢的钉身正是漏斗的形状。改成斜 45° 后轮廓才立得住。

坐标是**按 45° 轴算出来**的，不是把正向版本整体 `rotate()`：绕三个不同中心各转过
一次，钉身与钉子都糊在一起、钉尖带上灰度拖影（旋转把描边推离了像素栅格）。详见
[自绘图标](custom-icons.md)。

### 图钉字形：十余个候选筛到一个

官方 primitives 的导出表里**没有任何图钉**（整张表核过），置顶按钮因此需要自绘。
做法与既有的工作区分组字形相同：渲染候选 → 按真实 16px 栅格化 → 最近邻放大成像素图
逐个看 → 用 `magick ... -depth 8 gray:-` 枚举墨迹范围。

被否掉的造型与原因（详见 [自绘图标](custom-icons.md)）：

| 造型 | 否掉的原因 |
| --- | --- |
| 矩形钉身 + 竖线钉子 | 读成一张小桌子，钉身与钉子之间没有「收拢」这个动作 |
| 钉身占满 `4.4~11.6` | 填充版变成一块实心方块 |
| 尖角折角 | 16px 下尖角被栅格吃掉，钉身读成一个实心三角 |
| 钉子短于 `13.6` | 整体像一个带柄的碗，「钉」读不出来 |

定稿的墨迹是 x `3~12`、y `3~13`：纵向与官方文件夹（y `2.429~13.5863`）同域，
并排时不会一个高一个矮。

### 第二行的截断：负外边距会吃掉内容宽度

标题块需要 4px 的命中余量才能让悬停底色包住文字。第一版把它做成「`.wg-header` 留
4px，标题块用 `margin-left: -4px` 抵回来」，视觉上对齐了，但实测 `focusClipped: true`
——负外边距**同时缩小了标题块的内容尺寸**，第二行只剩「全部工…」。

改为**命中余量由标题块自己带（`padding: 2px 4px`）、基线那条撤成 0**：两行在同一个
按钮盒子里因此天然同一条左缘（实测两行的文字左缘都是 16px），而第二行不再被截断
（`focusClipped: false`）。这条用 `test/styles.test.ts` 把「第二行不得自带内边距 /
标题块不得用负外边距」钉住——它是一个只会表现为「文字少了几个字」的静默失效。

### 头部高度：36px 会吞掉第二行

两行各 20px 行高加 4px 下间距是 44px，而 header 带 `overflow: hidden`（搜索展开时
标题要整块收拢淡出）。沿用官方那条 36px 定高会把第二行连同裁剪一起吞掉，界面上只是
「聚焦的那一行不见了」，不会有任何报错。实测带两行标题时 header 高度是 40px
（两行 40px 撑满，`height: auto` 生效）。

### 面板底色：用错 token 会整条失效

面板是**不透明的浮层**，底下就是会话列表。第一版把它写成
`background: var(--dsw-alias-bg-elevated, var(--dsw-alias-bg-primary))`、
`box-shadow: var(--dsw-shadow-popover, ...)`——这两个 token 名并不存在（主题里真实的
是 `--dsw-specific-menu` 与 `--dsw-elevation-prominent`）。`var()` 引用一个未定义的
自定义属性会让**整条声明失效**（而不是退回回退值，回退值只在属性本身未被赋值时生效），
于是 `background` 整条被丢掉，面板变成透明的，后面的会话直接穿过来。

这条错误的危险之处在于它完全静默：没有报错、`tsc` 不管 CSS、单测从源码读样式表也照样
通过（样式表的文本确实写着那个属性）。修法是照官方 `.list` / `.submenu` 面板那一份值
逐条取（见 [布局与样式对齐](layout-and-styling.md)），并让测试**点名断言那几个 token**、
同时禁止带回退值的写法——回退值会把「token 名写错」伪装成「悄悄用了另一个颜色」。

实测复核：`getComputedStyle(panel).backgroundColor` 在浅色主题下解析为
`rgb(255, 255, 255)`（`--dsw-specific-menu` → `--dsw-alias-bg-layer-3` →
`--dsw-static-neutral-bluish-00`），`box-shadow` 是那圈 .5px 描边加两层柔和投影。

### 菜单开合的两处可见信号

`getComputedStyle` 实测：箭头在菜单打开时 `transform` 为 `matrix(-1, 0, 0, -1, 0, 0)`
（即 `rotate(180deg)`）；未置顶的置顶按钮 `opacity: 0` 且 `pointer-events: none`，
已置顶的是 `opacity: 1`。这两条都断言在计算样式上而不是源码文本上。

## 顺带修掉的一处偶发失败

`test/render.test.ts` 里那个 props 夹具给每一行各调了一次 `Date.now()`，两行的
`updatedAt` 因此有约 **0.2%** 的概率落在相邻的两个毫秒里（实测 20 万次跨了 364 次）。
搜索结果按 `updatedAt` 倒序，而 `a` 与 `orphan` 都命中同一个查询词，于是哪一行排在
前面随运行而变——断言「路径分成两段着色」的那条用例会偶发地拿到没有分组的那一行。

它表现为约 1/30 的偶发失败，且**看不到失败时会以为一切正常**。修法是让整个夹具共用
一次取到的时间基准，并让 `orphan` 明确比 `a` 早一秒：排序从此完全确定。这条与选择器
无关，是动手时顺手撞上的。
