# 子工作区嵌套

一个工作区可能落在另一个工作区的目录下（`/repo` 与 `/repo/a`）。开启嵌套后，子工作区不再与父工作区并列在根节点，而是在父工作区体内的撑开体里渲染，层级因此与目录结构一致。

## 与两套分组的分工

本包此前有两套容器，都是「手动建、手动移入」的：

| 层级 | 容器 | 装什么 | 在哪 |
| --- | --- | --- | --- |
| 根节点 | **工作区分组**（虚拟工作区） | 工作区 | 列表最外层 |
| 工作区内 | **会话分组** | 会话 | 某个工作区内部 |

子工作区是第三种关系，与前两者正交：

- **父子关系不落盘**。它由工作区的 `cwd` 现推——`cwd` 是工作区自己的事实，落盘只会多一份可能与它偏离的副本。因此新建一个工作区、或改一个目录名之后，层级自动跟着变。
- **放进分组的那条归属落盘**，但它记在**子工作区自己**的记录上（见[数据存储](data-storage.md#嵌套归属)），不是往父工作区的分组里追加成员。一个子工作区因此天然只能有一个归属。
- **会话分组里可以放子工作区**。放进某个分组的子工作区渲染在那个分组的撑开体里，与组内会话同列；没放进任何分组的子工作区渲染在父工作区体内「未归组」那一段。

## 父子关系怎么判定

**只有同处一个虚拟工作区分组、或两者都不在任何分组里的工作区才成父子。** 把同一个项目下的一组工作区收进一个虚拟分组之后，它们之间的 cwd 层级仍然保留——收进去不该把层级抹平。分属两个虚拟分组的工作区则不相连：它们在列表上读作两片互不相干的内容，即便路径上确实是父子。

在这个范围之内，三个条件同时成立才是父子，全部在客户端推导：

1. **同一作用范围**：两者在同一个虚拟工作区分组里，或都不在任何虚拟工作区分组里。
2. **路径**：父的 `cwd` 是子的严格祖先目录，按路径段比较而不是字符串前缀——`/repo/a` 不是 `/repo/ab` 的父。
3. **父取最近的现存祖先**：中间层工作区没有登记时跨过去挂到更远的祖先，层级不会因为少登记一个目录而整段断开。深度因此任意层，不是固定两层。

一条落盘的归属还要再满足：父工作区与那个分组都还在、父确实是它的祖先、父与子同处一个虚拟工作区。任一条件不满足就退回按路径推导的位置——元数据与真实列表出现偏差时界面只是「少一层嵌套」，不会丢工作区。

路径比较的落地细节：分隔符统一成 `/`、去掉末尾多余的斜杠，`/` 与 `C:/` 这类根归一成空串后作为任何绝对路径的祖先。

## 渲染位置

列表上每一段只渲染**它这一段的顶层**工作区，被嵌套的那些由父工作区带出来：

| 容器 | 内容 |
| --- | --- |
| 根节点那一段 | 不在任何虚拟工作区、且没有被嵌套的工作区 |
| 某个工作区分组体内 | 该分组里没有被嵌套的工作区 |
| 某个工作区体内「未归组」那一段 | 没放进任何分组、且父是当前工作区的子工作区 |
| 某个会话分组体内 | 放进该分组、且父是当前工作区的子工作区 |

一个工作区**没有自己的归属**时，它落在父所在的那一段；有归属时落在父体内那个分组里。后一条是「整棵子树跟着父走」的实现：把 `/repo` 放进某个分组时，`/repo/a`、`/repo/a/b` 都在它体内，自然一起过去，不需要为每个后代改写归属。

### 归属与渲染是两件事

`buildRootLayout` 交出的每个分组段因此带两格：`workspaceIds` 是**归属**（该分组名下的全部工作区，内嵌的也算），`roots` 是**渲染**（这一层真正要列出来的）。开启嵌套时两者不同。

把它们合成一格会让「它已经在某个分组里」在内嵌之后读不出来——`/src/dsh_plugins/packages/dsh-workspace-groups` 归属 `dsh plugins` 这个虚拟分组，但它渲染在 `/src/dsh_plugins` 体内，因此不在该分组的 `roots` 里。只看 `roots` 的话，「移动到…」子菜单会把这个工作区**已经在的**那个分组再列一次，点下去是把一个无意义的操作摆在那里。

读 `workspaceIds` 的地方（归属查询、分组行右端的计数、空分组判据）与读 `roots` 的地方（组体渲染、聚焦后的列表切分）因此各取所需，不互相借用。

反过来，**父工作区体内分三段，顺序是「子工作区 → 会话分组 → 平铺会话」**（会话分组内部同序）。先文件夹后文件是资源管理器的惯性；会话分组排中间是因为它既可能装会话也可能装子工作区，放在两者之间才不会把同类的东西切开。

### 三段靠指示器区分，不再用小标题

三段的行文字左缘**不再**落在同一条竖线上：会话行的状态指示器绝对定位在行的左侧、不占行内流，因此它的标题比同级容器的名字左一格，缩进自己就说明了「这一段是会话」。原先那条「会话」小标题（12px、`label-caption`、12px 上间距）因此整个去掉了——它嵌套一深就在每个体内都冒一条，而它自己也不带图标、不带折叠，混在容器行里读起来更糊。

去掉它之后又不必再判断「体内还有没有别的东西」：那条件本是用来决定这条标题要不要渲染的。段序仍是「子工作区 → 会话分组 → 平铺会话」。

取值与落点见[布局与样式对齐](layout-and-styling.md#状态指示器)，六种解法的实测几何见[会话行指示器的备选方案](session-row-indicator/README.md)。

## 开关

header 右侧的**视图选项**按钮打开一个自绘面板，里面是「子工作区嵌套」这个开关，用官方 `Switch` 原语渲染。**默认开启。** 面板里它上面还有一组「展示方式」（按工作区 / 平铺），两组之间以分隔线隔开，见[展示方式](ui-details.md#展示方式)。

文案给的是**设置名**而不是「启用 / 关闭」这类动作短语：开关的开合本来就由 `aria-checked` 与滑块位置表达，文案再跟着状态变，读屏会读出「关闭子工作区嵌套，开关，已打开」这种自相矛盾。条目行本身因此不可点——`Switch` 已经是一个 `role="switch"` 的按钮，行再做成可点就是一层里两个控件。

| 状态 | 行为 |
| --- | --- |
| 开启 | 按 `cwd` 推导出的层级渲染；放进分组的子工作区渲染在父体内那个分组里 |
| 关闭 | 所有工作区回到它所属虚拟工作区分组（或根节点）平铺，缩进全部归零；落盘的归属**不清空** |

**关闭前弹一次确认，并列出会被解除嵌套的工作区**：那是「被放进某个分组」的那批。开关一关，它们就不再渲染在父体内，界面看起来与没有这个特性时完全一样，用户需要先知道自己关掉了什么。未放进任何分组的子工作区不在名单里——它们本来就只是按路径推导出来的展示层级，重新开启即回来。

关闭后列表底部常驻一行说明（`role="status"`），末尾那句点明「重新启用只恢复由目录路径推导出的层级，放入分组的记录不会回来」：关闭时归属已被清空，重新开启不会把那次放入分组找回来。

**关了又开不会恢复放入分组的记录**，这是刻意的取舍：留着一份「关闭期间不渲染、重新打开才生效」的隐藏状态，会让关掉时的界面与磁盘不一致，而用户关掉它的意图通常就是不要那些分组。

开关与归属清理合成一次写入（宿主 `setNested`），避免「开关已关、归属还在」有一段可观察的窗口。

## 归组入口

子工作区要进父工作区的分组，走工作区行 `...` 菜单里的**「移动到分组…」**一级项，它下面列出祖先工作区体内可移入的分组。与既有的「移动到…」（进根节点的虚拟工作区分组）平级但互不影响：两者进的是不同层级的容器，菜单里各成一个块、块间画分隔线。

- **父是「放谁的分组」决定的**，不是自动取最近祖先。cwd 路径上有多个现存祖先时，子菜单列出每个祖先名下的分组；只有一个祖先时分组名本身就是唯一的坐标，不再挂祖先名，标签因此对齐。
- **没有可移入的目标、且当前也不在任何分组里时整项不渲染**，不留点不动的死入口。这与虚拟工作区分组那一项不同——那一项的子菜单里总有一个「新建」可点。
- **「移出分组」**与它平级、紧跟在下方，仅当前已归组时出现。

## 放进分组时子工作区怎么跟随

把工作区 `A` 放进祖先 `X` 的分组 `G` 时，`A` 名下**已经放进某个分组**的子工作区一并换到 `G`，保持层级关系。没放进任何分组的那些由路径推导自动跟随，不需要改写归属。因此这一次操作会一次写多份归属（宿主 `nestWorkspaces` 收一批 id），父已进组、子还留在原组是一段可恢复的中间态。

### 新增工作区时先问一句

「添加工作区」采纳成功后，如果新工作区落在某个现存工作区之下，而那个父工作区**恰好只在一个分组里**，就弹一个确认框问要不要顺手放进去。父不存在、父不在任何分组里、或父有多个分组时不问——前两种情况下默认的嵌套渲染已经把它放在父下面，最后一种该选哪个分组不是这里能替用户定的。

这两个流程的差别在**用户意图是否明确**：`A` 是被用户主动移进某个分组的，「整棵子树跟着走」就是那条操作的意思；新工作区则是采纳目录的副作用，顺手改它的归属需要先问。

同一个回调还要先把该展开的几层展开：采纳之后紧接着会在新工作区里开一个新会话并聚焦过去，而新工作区默认折叠，不展开就落在看不见的撑开体里。展开范围是「新工作区自己 + 它的父链」，且**只在真的找得到父时**才做——判据与上面那条「放进分组」用的是同一次路径查找，因此「找到了父」就等于「它真的会渲染在那个父体内」。找不到父、或关掉了嵌套时不写任何记录，那时它落成自己那个容器的顶层、本来就默认展开。见[数据存储](data-storage.md#采纳路径的展开)。

## 折叠与展开

| 状态 | 键 | 默认 |
| --- | --- | --- |
| 工作区展开 | `workspaceId`（子工作区各用自己那一份，互不影响） | 无父展开、有父折叠 |
| 会话分组展开 | `<workspaceId>:<groupId>` | 折叠 |
| 工作区分组展开 | 虚拟工作区分组 id | 展开 |

三份记录都存在浏览器本地 store 里（见[数据存储](data-storage.md)），键缺席表示用户从未碰过这一层，此时按上表的默认现推。因此**子工作区默认是收起的**，一层层点开才能看到更深的目录。

搜索里点开一条结果时，那条会话所在工作区的**全部祖先**会逐层展开：只展开它自己会让那一行落在收起的父撑开体里，用户看不到它。这里的判据是「除非显式展开，否则写展开」——与官方揭示 effect 的「只在显式为 `false` 时才写」不同，因为本包对子工作区与会话分组的默认是折叠，缺键必须被显式补上。

## 缩进

缩进不再按固定层数写死选择器——子工作区可以任意层。层级由嵌套推导（`data/nest.ts` 的 `levelOf`）算出，组件经 `--wg-depth` 下发：

- 它数的是**渲染结构上让出了几格**，不是 cwd 祖先个数。
- 在虚拟分组里、组内没有更近的父：`1`（工作区分组是这条链上的第 0 层）。
- 挂在父体内未归组那一段：父的层级 `+1`。
- 放进父体内某个会话分组：父的层级 `+2`——多出来的一格是中间那个分组头，这样它才与同组的会话行同档。
- 每层让出一个 16px 图标列，基准是官方工作区行的 8px：工作区行 `8 + 16d`、分组头 `24 + 16d`、未归组会话 `24 + 16d`、组内会话 `40 + 16d`。

层级**必须在 JS 里算，不能靠 CSS 变量继承累加**：把一个变量定义成它自己加一是循环引用，浏览器会丢掉整条声明，缩进静默失效。

每个 `.workspace` 都自己下发一次 `--wg-depth`，子工作区因此不会被父的深度顺着继承下来。引导线读同一个值，行与线不会错位。取值来源见[布局与样式对齐](layout-and-styling.md#层级缩进)。

## 工作区选择器里的子工作区

菜单的条目按两条规则决定：

| 工作区 | 在菜单里 |
| --- | --- |
| 属于某个虚拟工作区分组 | 只列那个分组，**它名下的成员不单独列出** |
| 不属于任何虚拟工作区分组 | 按 cwd 嵌套层级展开，子工作区按 `--wg-picker-depth` 缩进 |

**虚拟工作区分组只显示它自己。** 聚焦这个分组与聚焦它名下的某个成员指向同一片内容，把成员列出来只会让菜单多出一层与列表重复的层级。因此菜单里没有「成员」这一档：`dsh plugins` 这样一个分组名就是它名下全部工作区的入口。

**菜单里按层级展开的只有未归组那一段。** 归组的工作区由分组名一个条目代表，不是因为它没有层级——同一个虚拟分组内部的父子关系在列表里照常渲染（见「父子关系怎么判定」），只是不在菜单里各占一行。

菜单因此可能出现指向已消失条目的陈旧记录——某个工作区被移进虚拟分组后，它此前的聚焦 / 置顶 / 最近使用记录仍然存在。`pickerSections` 按现存条目过滤，这类记录被静默丢弃；聚焦记录解析不到时退回整片内容，而不是把列表切成空的一片。

## 降级路径

| 情形 | 行为 |
| --- | --- |
| 快照缺 `nesting` / `nested`（旧宿主半边） | `normalizeSnapshot` 补齐：归属按空、开关按开启 |
| 工作区没有 `cwd` | 它不参与嵌套，作为自己那一段的顶层渲染 |
| 归属指向已删除的分组或工作区 | 该条归属不生效，退回按路径推导的位置 |
| 父指针成环（元数据被手改） | 祖先链上带 `seen` 去重，不让一行坏记录把界面挂死 |
